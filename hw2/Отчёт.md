## Сборка образов

Образов два:

| Образ | Из чего | Зачем |
|---|---|---|
| `trade-app:0.1.0` | `Dockerfile` в корне (остался с первого задания) | само приложение |
| `trade-migrate:0.1.0` | `hw2/migrate.Dockerfile` | миграции базы |

Второй образ пришлось сделать, потому что в compose миграции подключались в контейнер `migrate/migrate` как папка с диска (volume `./migrations`). В Kubernetes папку со своего компьютера так просто не подключишь, поэтому я сделал образ на основе `migrate/migrate:v4.18.1` и скопировал миграции внутрь. Так миграции версионируются вместе с образом.

Теги не `latest`, а `0.1.0`, и в манифестах `imagePullPolicy: IfNotPresent`. С тегом `latest` Kubernetes по умолчанию пытается скачать образ из Docker Hub, а моего образа там нет.

Собирал двумя способами.

**1. Сразу в docker-демоне minikube** (как в задании). Внутри minikube работает свой Docker, отдельный от Docker Desktop, и Kubernetes берёт образы оттуда. В задании команда для bash, у меня Windows, поэтому в PowerShell:

```powershell
& minikube -p minikube docker-env --shell powershell | Invoke-Expression
docker build -t trade-app:0.1.0 .
docker build -f hw2/migrate.Dockerfile -t trade-migrate:0.1.0 .
```

Первая команда переключает `docker` в текущем терминале на демон minikube, и образ сразу собирается внутри кластера.

**2. Собрать обычным Docker и загрузить в minikube:**

```powershell
docker build -t trade-app:0.1.0 .
docker build -f hw2/migrate.Dockerfile -t trade-migrate:0.1.0 .
minikube image load trade-app:0.1.0
minikube image load trade-migrate:0.1.0
```

Проверить, что образы есть в кластере: `minikube image ls | findstr trade`.

## Какие абстракции Kubernetes использованы

Все манифесты лежат в `hw2/k8s/`, один объект на файл. Номер в имени файла - это порядок: `kubectl apply -f hw2/k8s/` применяет файлы по алфавиту, поэтому namespace создаётся первым. Нумеровал десятками по группам (0x - общее, 1x - база, 2x - миграции, 3x - приложение), чтобы можно было добавить файл внутрь группы.

Как сервисы из compose переехали в Kubernetes:

| docker compose | Kubernetes |
|---|---|
| `.env` | Secret `postgres-credentials` + ConfigMap `trade-app` |
| сервис `postgres` + volume `pgdata` | StatefulSet `postgres` + PersistentVolumeClaim + Service `postgres` |
| сервис `migrate`, `depends_on: service_healthy` | Job `trade-migrate` + initContainer, который ждёт базу |
| сервис `app`, `depends_on: service_completed_successfully` | Deployment `trade-app` + initContainer, который ждёт миграции |
| `healthcheck` у `app` | readinessProbe и livenessProbe |
| `ports: 8080:8080` | Service `trade-app` типа NodePort |

Дальше по каждой абстракции.

### Namespace (`00-namespace.yml`)

Всё приложение лежит в namespace `trade`. На семинаре всё создавалось в `default`, но мне так удобнее: `kubectl -n trade get all` показывает только мой проект, а `kubectl delete namespace trade` удаляет всё разом, включая диск базы.

### Secret (`01-secret.yml`)

Secret `postgres-credentials` хранит логин, пароль, имя базы и готовую строку подключения `DATABASE_URL`. Из него берут значения все три компонента:
- Postgres - `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` (официальный образ postgres по ним создаёт пользователя и базу при первом запуске);
- Job миграций и приложение - `DATABASE_URL`.

Подключал как на семинаре, через `env` + `secretKeyRef`. В манифесте использовал `stringData`, чтобы писать значения обычным текстом, а не в base64.

Сначала я собирал `DATABASE_URL` прямо в манифесте из кусков через `$(DB_USER)`, `$(DB_PASSWORD)` и т.д., чтобы пароль не повторялся. Но когда добавились initContainers, этот блок пришлось бы копировать в 4 контейнера, и я положил готовую строку в тот же Secret.

### ConfigMap (`02-configmap.yml`)

ConfigMap `trade-app` - несекретный конфиг приложения: `HTTP_ADDR=:8080` и `SHUTDOWN_TIMEOUT=10s`. На семинаре ConfigMap монтировался как файл (конфиг nginx), а у меня приложение читает конфиг из переменных окружения, поэтому подключаю через `envFrom` - все ключи ConfigMap становятся переменными.

### Pod

Pod - минимальная единица запуска, один или несколько контейнеров с общей сетью. Напрямую поды я не создаю, их создают контроллеры ниже (Deployment, StatefulSet, Job). Если под умирает, контроллер создаёт новый, а одиночный Pod никто бы не пересоздал.

### StatefulSet для Postgres (`10-postgres-statefulset.yml`)

Этого на семинаре не было. StatefulSet похож на Deployment, но сделан для приложений с данными:
- у пода постоянное имя `postgres-0`, а не случайное, как у Deployment;
- через `volumeClaimTemplates` для каждого пода создаётся свой диск (PVC `data-postgres-0`), и после пересоздания под подключается к тому же диску;
- поды запускаются и останавливаются строго по очереди.

Если сделать базу через Deployment, то при обновлении Deployment сначала поднимет новый под, а потом удалит старый, и два Postgres какое-то время будут пытаться работать с одними файлами. StatefulSet так не делает.

Реплика одна. Несколько реплик StatefulSet - это не кластер Postgres: каждая получит свой пустой диск, и данные между ними синхронизироваться не будут. Для настоящей репликации нужен оператор (например CloudNativePG) или managed-база, для учебного проекта это лишнее.

Ещё в этом манифесте:
- `PGDATA=/var/lib/postgresql/data/pgdata` - данные в подпапке тома (так советуют в описании образа postgres, иначе на некоторых дисках initdb ругается на непустую папку);
- readiness и liveness через `pg_isready`;
- `resources`: запрос 0.1 CPU и 256 МБ памяти, лимит 0.5 CPU и 512 МБ.

### PersistentVolumeClaim, PersistentVolume, StorageClass

Это тоже сверх семинара. PVC - это заявка «мне нужен диск на 1 ГБ с доступом на запись с одной ноды» (`ReadWriteOnce`). В minikube по умолчанию есть StorageClass `standard`, он сам создаёт под заявку PersistentVolume (папку на ноде minikube) и связывает их. Я проверял: удалил под `postgres-0`, StatefulSet пересоздал его с тем же PVC, и все лоты остались на месте.

### Service (`11-postgres-service.yml`, `31-app-service.yml`)

Service даёт постоянное имя и IP группе подов, которую выбирает по label (`selector: app: ...`), как на семинаре. Поды пересоздаются, и их IP меняются, а адрес Service нет. Трафик Service отправляет только в поды, которые прошли readinessProbe.

- `postgres` - тип ClusterIP (доступен только внутри кластера), порт 5432. По этому имени приложение и миграции ходят в базу: `postgres://...@postgres:5432/trade`.
- `trade-app` - тип NodePort, порт 80 -> 8080 в контейнере, на ноде открыт порт 30080. NodePort нужен, чтобы зайти в приложение снаружи кластера, ClusterIP из браузера не открыть.

### Job для миграций (`20-migrate-job.yml`)

Миграции - разовая задача (фактор XII из 12 факторов), поэтому это Job, а не Deployment: под отработал, завершился со статусом `Completed`, и Kubernetes его не перезапускает. Как на семинаре, указаны `restartPolicy: Never`, `backoffLimit: 6` (сколько раз повторить, если упал) и `activeDeadlineSeconds: 300` (больше 5 минут не ждать).

Job нельзя изменить после создания. Если поменять его манифест (например тег образа), перед `apply` нужно удалить старый: `kubectl -n trade delete job trade-migrate`. Если манифест не менялся, повторный `apply` просто пишет `unchanged`.

### Deployment и ReplicaSet для приложения (`30-app-deployment.yml`)

Приложение без состояния, поэтому Deployment. Deployment создаёт ReplicaSet, а ReplicaSet следит, чтобы подов было ровно столько, сколько указано в `replicas` (у меня 2). При обновлении образа Deployment создаёт новый ReplicaSet и постепенно переводит поды на него, это было на семинаре через `kubectl set image`.

Что я настроил:
- **`strategy: RollingUpdate`** с `maxSurge: 1` и `maxUnavailable: 0`. На семинаре было `1/1`, но тогда при обновлении один из двух подов сразу удаляется. С `maxUnavailable: 0` старый под удаляется только тогда, когда новый уже готов.
- **readinessProbe** на `/readyz`: приложение проверяет связь с базой. Если базы нет, под помечается неготовым, и Service перестаёт слать в него запросы.
- **livenessProbe** на `/healthz`: просто «процесс жив». Специально не зависит от базы: если база упала, перезапуск приложения её не починит, только лишний раз всё перезапустит.
- **`resources`**: запрос 0.05 CPU и 32 МБ, лимит 0.2 CPU и 128 МБ. Go-бинарник маленький, ему больше не нужно.
- **Корректная остановка.** При удалении пода Kubernetes одновременно шлёт SIGTERM и убирает под из Service, и какие-то запросы могут ещё успеть прийти в уже остановленный процесс. Поэтому добавил `preStop: sleep 5`: под сначала 5 секунд ждёт, пока его уберут из Service, и только потом получает SIGTERM. Затем приложение дорабатывает текущие запросы (до `SHUTDOWN_TIMEOUT` = 10 с). `terminationGracePeriodSeconds: 30` с запасом больше 5 + 10.
- **`securityContext`**: запуск не от root (uid 10001, как в Dockerfile), файловая система только для чтения, запрет повышения привилегий.
- **Аннотация `kubectl.kubernetes.io/default-container: trade-app`**: в поде два контейнера (initContainer и основной), и без неё `kubectl logs` каждый раз пишет, какой контейнер он выбрал.

### initContainers

Этого на семинаре тоже не было, но без них не получалось запустить всё одной командой. initContainer - это контейнер, который выполняется в поде до основного. Пока он не завершится успешно, основной контейнер не стартует.

- В Job: `wait-for-postgres` на образе `postgres:17-alpine` раз в 2 секунды делает `pg_isready`, пока база не начнёт принимать соединения.
- В Deployment: `wait-for-migrations` на образе `trade-migrate` ждёт, пока `migrate version` (текущая версия схемы в базе) не станет равна номеру последнего файла миграции в образе. Если я добавлю миграцию `000007`, манифест менять не придётся.

Без них при `kubectl apply -f hw2/k8s/` Job и поды приложения стартовали бы одновременно с базой и падали бы (`Error`, `CrashLoopBackOff`), пока база не поднимется. В итоге всё бы заработало само, но выглядит плохо. А ещё приложение могло бы начать отвечать раньше, чем применились миграции, и отдавать 500, потому что таблиц ещё нет.

## Как сервисы взаимодействуют между собой

```
 Браузер
   │  http://127.0.0.1:<порт>
   ▼
 minikube service (туннель с Windows внутрь minikube)
   │
   ▼
 Service trade-app (NodePort 30080 -> 8080)
   │  балансирует между готовыми подами
   ├──────────────────────┐
   ▼                      ▼
 Pod trade-app-...      Pod trade-app-...       ← Deployment / ReplicaSet, replicas: 2..N
   │  DATABASE_URL = postgres://...@postgres:5432/trade
   └──────────┬───────────┘
              ▼
 Service postgres (ClusterIP, 5432)  ← имя "postgres" резолвит DNS кластера (CoreDNS)
              │
              ▼
 Pod postgres-0  ← StatefulSet
              │
              ▼
 PVC data-postgres-0 -> PV (диск 1Gi в minikube)

 Job trade-migrate ── тоже ходит в Service postgres, применяет миграции и завершается
```

1. **Браузер -> приложение.** Фронтенд отдаёт тот же Go-процесс (`GET /`), а потом страница из браузера вызывает API по тому же адресу (`/v1/listings`). Снаружи в кластер запрос попадает через Service `trade-app` типа NodePort. У меня Windows и minikube на драйвере docker, поэтому IP ноды (`192.168.49.2`) с компьютера напрямую недоступен. `minikube service trade-app -n trade` открывает туннель на `127.0.0.1:<порт>`, и терминал с этой командой нужно держать открытым.
2. **Service -> поды приложения.** Service выбирает поды по label `app: trade-app` и отправляет запрос в один из готовых (прошедших readiness). Распределение идёт по TCP-соединениям, а не по отдельным запросам, поэтому браузер, который держит соединение открытым, какое-то время ходит в один и тот же под.
3. **Приложение -> база.** В `DATABASE_URL` указан хост `postgres`. Внутри кластера это имя резолвит CoreDNS в IP Service `postgres` (полное имя `postgres.trade.svc.cluster.local`), а Service передаёт соединение в под `postgres-0`. Приложение не знает IP базы, и после пересоздания пода базы ничего менять не нужно.
4. **Миграции -> база.** Job ходит в ту же базу через тот же Service, применяет миграции и завершается.
5. **Реплики приложения между собой не общаются вообще.** Всё состояние (лоты и ключи идемпотентности) лежит в Postgres. Если два покупателя попали на разные поды и покупают один лот, разруливает база через `SELECT ... FOR UPDATE`. Я это проверял: 20 параллельных покупок одного лота на 4 репликах дали ровно один ответ `200` и 19 ответов `409`.

### Порядок запуска

Всё запускается одной командой `kubectl apply -f hw2/k8s/`. kubectl сам ничего не запускает: он отправляет все 8 объектов в kube-apiserver, и дальше каждый контроллер создаёт свои поды. Все поды создаются одновременно, а порядок получается из initContainers:

```
0s   postgres-0       ContainerCreating   база стартует
0s   trade-migrate    Init:0/1            init ждёт pg_isready
0s   trade-app × 2    Init:0/1            init ждёт миграцию 6
7s   postgres-0       1/1 Running         база готова, Service postgres пускает в неё трафик
9s   trade-migrate    PodInitializing     pg_isready ответил
10s  trade-migrate    Completed           миграции применены
11s  trade-app × 2    PodInitializing     версия схемы = 6
12s  trade-app × 2    1/1 Running         readiness прошёл, Service trade-app пускает трафик
```

Namespace, Secret, ConfigMap и Service - не поды, они ничего не запускают, а просто сохраняются в кластере в момент `apply`, раньше всех подов.

## Масштабирование

Масштабируется только приложение:

```bash
kubectl -n trade scale deployment/trade-app --replicas=4
```

Это работает, потому что приложение stateless (фактор VI), а новые поды при старте проходят initContainer мгновенно - миграции уже применены. Postgres остаётся в одной реплике (почему - написал выше в разделе про StatefulSet).

Заметил одну вещь: `kubectl scale` меняет число реплик только в кластере, а в манифесте осталось `replicas: 2`. Если после этого снова сделать `kubectl apply -f hw2/k8s/`, реплик опять станет 2. Чтобы реплик было больше постоянно, нужно менять манифест. В реальном проекте число реплик менял бы HorizontalPodAutoscaler по нагрузке.

В первом задании я писал, что `docker compose up --scale app=3` не работает из-за проброса порта `8080:8080`. В Kubernetes этой проблемы нет: у каждого пода свой IP, а наружу смотрит один Service.

## Что я проверял

Тесты слал из отдельного пода с curl внутри кластера, на адрес Service `http://trade-app.trade.svc.cluster.local`.

- Все ручки API отвечают так же, как в первом задании: создание, изменение цены, покупка, отмена, повтор с тем же `Idempotency-Key` возвращает тот же ответ, неверный ключ - `401`, лот чужой игры - `404`.
- Масштабирование до 4 реплик: запросы разошлись по всем подам (11/11/19/20 из 61), гонка 20 покупателей - 1×`200`, 19×`409`.
- Обновление приложения под нагрузкой (поменял шаблон пода, Deployment заменил оба пода): за это время ушло 733 запроса, все `200`, ни одной ошибки.
- Удалил под `postgres-0`: StatefulSet пересоздал его с тем же диском, данные на месте.
- Выключил базу (`kubectl scale statefulset/postgres --replicas=0`): примерно через 15 секунд (3 неудачные проверки по 5 секунд) поды приложения стали `0/1` и Service перестал отправлять в них запросы. Перезапусков не было, потому что liveness от базы не зависит. После включения базы поды сами вернулись в `1/1`.
- `kubectl delete -f hw2/k8s/` удаляет всё вместе с диском, повторный `apply` поднимает всё с нуля.

Ещё одно наблюдение: если открыть приложение через `kubectl port-forward svc/trade-app`, то все запросы уходят в один под (у меня 40 из 40). port-forward выбирает один под и обходит балансировку Service. Через `minikube service` запросы распределяются по всем подам, поэтому для демонстрации я использую его.

## Как запустить

Нужны Docker Desktop и minikube.

```powershell
minikube start --driver=docker --container-runtime=docker --kubernetes-version=v1.35.8 --cpus=4 --memory=4096

& minikube -p minikube docker-env --shell powershell | Invoke-Expression
docker build -t trade-app:0.1.0 .
docker build -f hw2/migrate.Dockerfile -t trade-migrate:0.1.0 .

kubectl apply -f hw2/k8s/
kubectl -n trade get pods -w

minikube service trade-app -n trade
```

Последняя команда сама открывает браузер. Дальше можно войти под именем `vasya`, выставить лот, во второй вкладке войти как `petya` и купить его.

Удалить всё: `kubectl delete -f hw2/k8s/` (или `kubectl delete namespace trade`).

## Ограничения

- Пароль от базы лежит в `01-secret.yml` в репозитории. Secret в Kubernetes - это просто base64, а не шифрование. Для учебного проекта так нормально, в реальном проекте секрет создавали бы отдельно (`kubectl create secret` из CI или через Sealed Secrets / Vault) и в git не клали бы.
- Postgres в одном экземпляре и без бэкапов. Если удалить namespace, данные пропадут вместе с PVC.
- Для доступа снаружи использую NodePort и `minikube service`, а не Ingress. Ingress и балансировку я планирую разобрать в следующем задании.
- API-ключ игры, как и в первом задании, хранится во фронтенде - это допущение только для демо.
