# Отчёт по заданию 1

## Доменная область

Мой проект называется Trade for All. Это сервис-торговая площадка для онлайн-игр, которые не выходят в Steam (itch.io, VK Play, свои лаунчеры и т.д.). У таких игр обычно нет нормального способа меняться предметами: игроки договариваются в Discord, кто-то отдаёт предмет первым и его обманывают. А писать свою торговую площадку маленькой инди-студии долго и сложно.

Идея в том, что разработчик игры подключает мой сервис по REST API и получает готовую торговлю: игрок выставляет предмет на продажу за внутриигровую валюту, другой игрок покупает. Реальных денег в сервисе нет вообще, только игровая валюта, поэтому не нужно связываться с платежами и налогами.

Схема такая:

```
клиент игры -> сервер игры -> Trade for All
```

1. Игрок нажимает "продать меч". Сервер игры забирает меч из инвентаря и создаёт лот у меня. Пока лот висит, предмет существует только в лоте (это и есть эскроу).
2. Другой игрок нажимает "купить". Сервер игры списывает у него валюту и вызывает покупку. В ответе я возвращаю, кому выдать предмет и кому сколько начислить.
3. Если продавец снимает лот, я возвращаю, какой предмет ему вернуть.

Главная сложность - не допустить дюпа (размножения предметов или валюты), если два игрока покупают один лот одновременно, или если запрос дошёл, а ответ потерялся и игра повторила запрос.

## Стек

- **Go 1.25** - бэкенд. Роутинг на стандартном `net/http` (в Go 1.22+ там уже есть методы и параметры в путях, так что сторонний роутер не понадобился), логи через `log/slog`.
- **PostgreSQL 17** - хранение данных. Транзакции и `SELECT ... FOR UPDATE` нужны, чтобы лот нельзя было купить дважды.
- **pgx/v5** - драйвер Postgres для Go, пул соединений.
- **golang-migrate** - миграции базы (схема + тестовые данные).
- **Docker, docker compose** - запуск всего окружения одной командой.
- **Фронтенд** - одна HTML-страница на чистом JS без фреймворков и сборки. Она встраивается в бинарник через `go:embed` и отдаётся тем же Go-сервером. Выбрал так специально, чтобы стек был лёгким, как советуют в задании.

Структура проекта:

```
cmd/trade/main.go      точка входа, запуск и остановка сервера
internal/config        чтение конфигурации из переменных окружения
internal/domain        сущности и бизнес-правила (можно ли купить лот и т.д.)
internal/repository    работа с Postgres
internal/service       бизнес-логика, валидация, идемпотентность
internal/server        HTTP: роуты, хендлеры, middleware
internal/web           фронтенд
migrations             SQL-миграции
docs/api.md            спецификация API
```

## Сущности

**Игра (`games`)** - игра, которая подключилась к сервису. У неё есть API-ключ, по нему сервис понимает, из какой игры пришёл запрос. Все данные разделены по играм, одна игра не видит лоты другой. Регистрации игр через API пока нет, две тестовые игры создаются миграцией.

**Лот (`listings`)** - предмет, выставленный на продажу:
- `seller_id` - id игрока-продавца (это id из самой игры, своих игроков я не храню);
- `item_code` - тип предмета, например `iron_sword`;
- `quantity` - сколько штук;
- `price` - цена всего лота;
- `status` - `active`, `sold` или `cancelled`;
- `buyer_id` - покупатель, если лот продан.

**Ключ идемпотентности (`idempotency_keys`)** - техническая сущность. Каждый изменяющий запрос приходит с заголовком `Idempotency-Key`, и я сохраняю результат операции по этому ключу в той же транзакции, что и саму операцию. Если игра повторит запрос с тем же ключом (например после таймаута), она получит сохранённый ответ, а операция второй раз не выполнится.

### CRUD

| Операция | Ручка | Что делает |
|---|---|---|
| Create | `POST /v1/listings` | выставить лот |
| Read | `GET /v1/listings` | витрина с фильтрами и курсорной пагинацией |
| Update | `PATCH /v1/listings/{id}` | изменить цену лота |
| Delete | `POST /v1/listings/{id}/cancel` | снять лот с продажи |
| | `POST /v1/listings/{id}/buy` | купить лот |

Удаление у меня "мягкое": лот не удаляется из таблицы, а переходит в статус `cancelled`. Сделал так специально, потому что для торговли нужна история: по удалённой строке потом не разобраться, что произошло с предметом. Плюс по снятому лоту повторный запрос с тем же ключом должен вернуть тот же ответ, а для этого лот должен остаться в базе.

Подробно все ручки, форматы запросов и коды ошибок описаны в `docs/api.md`.

## Соответствие 12 факторам

### I. Кодовая база

Один репозиторий в git, одно приложение. Из одного и того же кода собирается образ и для локального запуска, и для любого другого окружения, отличается только конфигурация.

### II. Зависимости

Все зависимости Go явно объявлены в `go.mod` и зафиксированы в `go.sum`. Системных зависимостей у бинарника нет: он собирается с `CGO_ENABLED=0`, то есть статически, и запускается в голом `alpine`. Сборка идёт в Docker (multi-stage), поэтому на машине даже Go не нужен, только Docker. Утилита миграций тоже не ставится руками, а берётся готовым образом `migrate/migrate` с зафиксированной версией.

### III. Конфигурация

Вся конфигурация читается из переменных окружения (`internal/config/config.go`):
- `DATABASE_URL` - строка подключения к базе (обязательная, без неё сервис не стартует);
- `HTTP_ADDR` - адрес, на котором слушать (по умолчанию `:8080`);
- `SHUTDOWN_TIMEOUT` - сколько ждать текущие запросы при остановке.

В docker compose значения берутся из файла `.env`. Он добавлен в `.gitignore`, а в репозитории лежит шаблон `.env.example`. Паролей в коде нет.

Честно скажу про одно исключение: API-ключи двух тестовых игр записаны в миграции с сидами и во фронтенде. Это демо-данные для локального запуска, в реальной системе ключи выдавались бы при регистрации игры и хранились бы только на сервере игры.

### IV. Сторонние службы

PostgreSQL подключается как ресурс по `DATABASE_URL`. Чтобы переключиться на другой экземпляр Postgres (например managed Postgres в облаке вместо контейнера), достаточно поменять переменную, код менять не нужно. Локальная база и облачная для приложения ничем не отличаются.

С самой базой работает только слой `repository`, он написан на pgx под Postgres. Слой `service` про pgx не знает и зависит от интерфейса репозитория, поэтому в тестах бизнес-логики вместо Postgres подставляется реализация в памяти.

### V. Сборка, релиз, выполнение

Эти этапы разделены:
- **сборка** - `docker build`: в первом этапе Dockerfile компилируется бинарник, во втором он копируется в чистый образ;
- **релиз** - собранный образ + конфигурация из окружения;
- **выполнение** - `docker compose up` запускает готовый образ.

Миграции базы выполняются отдельным шагом перед стартом приложения (сервис `migrate` в compose), а не внутри кода приложения при запуске.

### VI. Процессы

Приложение не хранит состояние в памяти между запросами: все лоты и даже ключи идемпотентности лежат в Postgres. Сессий на сервере нет, игра определяется по заголовку `X-API-Key` в каждом запросе. Поэтому можно запустить несколько копий приложения, и они будут работать корректно. Повтор запроса может прийти на другую копию, и она всё равно найдёт сохранённый результат в базе.

### VII. Привязка портов

Приложение само является HTTP-сервером и слушает порт из `HTTP_ADDR`. Никакой внешний веб-сервер (nginx, apache) для работы не нужен. Фронтенд отдаёт этот же процесс.

### VIII. Параллелизм

Масштабирование делается запуском нескольких процессов, а не потоками внутри одного: так как процессы без состояния (фактор VI), их можно просто размножить. Одновременные операции над одним лотом из разных процессов разруливает база: лот блокируется через `SELECT ... FOR UPDATE`, поэтому даже если два покупателя пришли на разные копии сервиса, купит только один, а второй получит `409`.

Пока у меня есть ограничение: в `docker-compose.yml` порт приложения проброшен напрямую (`8080:8080`), поэтому `docker compose up --scale app=3` не сработает, все копии захотят один порт. Чтобы это починить, нужен балансировщик перед приложением. Его я планирую добавить в задании про балансировку трафика.

### IX. Утилизируемость

- **Быстрый старт.** Приложение - один бинарник, при старте только читает конфиг и проверяет подключение к базе (с таймаутом 5 секунд). Если база недоступна, сразу падает с понятной ошибкой, а не висит.
- **Корректная остановка.** По `SIGTERM` (так останавливает Docker) или Ctrl+C сервер перестаёт принимать новые соединения и ждёт, пока доработают текущие запросы (не дольше `SHUTDOWN_TIMEOUT`). Только после этого закрывается пул соединений с базой.
- **Устойчивость к внезапному падению.** Каждая операция идёт в одной транзакции вместе с сохранением ключа идемпотентности. Если процесс упадёт посреди операции, транзакция откатится целиком, и игра сможет повторить запрос с тем же ключом без риска дюпа.

### X. Паритет разработки и работы приложения

Локально всё запускается в тех же контейнерах, что и в любом другом окружении: та же версия Postgres (17), тот же образ приложения, те же миграции. Не бывает так, что локально используется SQLite, а на сервере Postgres.

### XI. Журналирование

Приложение пишет логи в stdout в формате JSON (`log/slog`) и ничего не знает про файлы логов. Собирает их среда выполнения, в моём случае Docker (`docker compose logs app`). На каждый запрос пишется строка с методом, путём, статусом и временем ответа, ошибки пишутся отдельно.

### XII. Задачи администрирования

Миграции - это разовая административная задача. Они лежат в том же репозитории (`migrations/`) и запускаются отдельным контейнером `migrate` в том же окружении и с той же базой, что и приложение. Тестовые данные (две игры и лоты) тоже добавлены миграциями, поэтому окружение всегда поднимается в одинаковом состоянии.

## Как запустить

Нужен только Docker.

```bash
cp .env.example .env
docker compose up --build
```

После этого:
- фронтенд: http://localhost:8080
- API: http://localhost:8080/v1/listings (с заголовком `X-API-Key: demo-survival-key`)

Тесты:

```bash
go test ./...
```

На фронтенде можно войти под именем игрока (например `vasya`) в одной вкладке и под другим (`petya`) в другой, выставить лот и купить его. Внизу страницы есть журнал запросов и кнопка "Повторить запрос", которая отправляет последний запрос с тем же ключом идемпотентности. Так видно, что повтор возвращает тот же ответ и лот второй раз не продаётся.

Важно: во фронтенде API вызывается прямо из браузера, и API-ключ игры хранится в нём. Это допущение только для демо, в настоящей игре запросы шли бы через сервер игры, а ключ хранился бы только там.
